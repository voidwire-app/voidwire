# voidwire threat model, draft v1 (M1)

*Protocol details: [PROTOCOL.md](PROTOCOL.md). Test coverage: [TEST-PLAN.md](TEST-PLAN.md).*

## 1. The mandatory requirement (core condition for no-prompt opening)

> **The URL opener can only ever receive URLs from a message that has been authenticated as coming from a cryptographically paired device in the owner's device group.**

Concretely, all of these MUST hold, and each is enforced in `voidwire-core`:

| # | Requirement | Where it's enforced | Tests |
|---|---|---|---|
| R1 | Unauthenticated or unpaired senders are rejected **before anything reaches the opener**. | `verify::Inbox::receive` steps 1–5: transport peer must be the link's one paired peer; inner sender must equal the transport peer; `verify_strict` Ed25519 signature; group/recipient match. | `tests/inbound.rs`: `unpaired_sender_rejected_before_parsing`, `attacker_own_valid_signature_is_not_authentication`, `sender_must_match_transport_peer`, `bad_signatures_rejected`, `weak_sender_key_rejected`, `signature_covers_every_field`, `forgotten_device_rejected` |
| R2 | A device is "paired" only after QR secret proof **and** the user typing the SAS. Pairing secrets are **single-use** (consumed on the first attempt of any kind) and **short-lived** (120 s, expired at ≥ 120 s, monotonic clock). | `pairing.rs`: `PairingRegistry::redeem`, `PairingGrant::confirm_typed_code`; a pairing link is built only from a completed pairing. | `pairing.rs` unit tests (single use, expiry boundaries 119.999/120/121 s, monotonic-not-wall, bad proof burns secret, transcript/name binding, typed SAS, SAS timeout, stuck RNG); ``pair2` tests` |
| R3 | Inbound messages are **rate-limited per device and per link**. Each pairing link has its own verifier, so the `global` bucket is per link: there is no budget shared across links. | `Inbox::receive` steps 6 and 10; defaults burst 5 / 10 per min per device, 20 per min global (`limits.rs`), configurable via `InboxConfig` within enforced floors/ceilings (D5). | `per_device_rate_limit_burst_and_recovery`, `invalid_authenticated_messages_count_against_device_limit`, `rate_limits_are_per_link_and_global_still_applies`, `default_limits_match_decision`, `inbox_config_floors_and_ceilings_d5` |
| R4 | Only **http/https** URLs under a **size cap** ever reach the OS opener, and never loopback/link-local/unspecified hosts (OQ-8). | `url_policy::check_url` (step 11) and again inside `SystemOpener::open`. QA p01, each must fail with its exact error), `static_assertions::assert_not_impl_any!` and `verified_url_from_foreign_inbox_cannot_open_auth_17` in `tests/inbound.rs`, bindings guard in `scripts/build-android.sh` |

## 2. How R6 is enforced in code

- `verify::VerifiedUrl` has **private fields** and **no public constructor**. The only `VerifiedUrl { .. }` expression in the codebase is the last line of `Inbox::receive_inner`, after all checks.
- It implements **no** `Clone`, `Copy`, `Default`, `From<String>`, `From<&str>`, `From<Url>`, `FromStr`, `Deserialize`. Checked at compile time by `static_assertions::assert_not_impl_any!` and by three `compile_fail` doctests (struct literal, `.into()`, `.clone()`).
- **The pairing's own inbox only (D2):** each link owns one `Inbox`, built from that pairing's binding (this device, the one peer, the pairing id); `receive(transport_peer, bytes, now)` has no membership parameter, and unpairing deletes the link with its inbox. Every `VerifiedUrl` carries a process-unique tag of the inbox that minted it.
- **Approval required (D2, AUTH-17):** `opener::UrlOpener::open(&self, approval: OpenApproval)` takes an `OpenApproval` **by value**. It has private fields and no `Clone`/`Default`/`From`/serde, and is minted only by `opener::deliver` (in `OpenImmediately` mode, the default since 10-11-2026, and only for a `VerifiedUrl`, i.e. after full verification) and `PendingOpen::confirm` (the user's click, with "Ask before opening" on). So the opener can't be called with a `String`, a `Url` or a bare `VerifiedUrl`, and each link opens at most once.
- `deliver` / `confirm` refuse a `VerifiedUrl` from another inbox (`ForeignInbox`) and re-check the sender's membership immediately before the open (closes the receive→open TOCTOU, REV-04).
- **One PC node per process (R1, M1):** a second live `PcNode::start` in the same process fails (`tests/one_inbox_per_process.rs`). The slot is released when that node is shut down or dropped, so the PC node can be cleanly restarted in-process (QA M1). Each pairing has its own verifier that accepts only that pairing's peer. Limits of this (by design): code running inside the app process (a malicious dependency, an injected DLL) could still call the opener's OS API itself, read the state file, or drive the UI. The types stop *accidental* bypasses in our code; **hostile in-process code is outside the guarantee** (same-user malware, §6.5).
- Nothing in `wire` exposes the URL of an unverified `SignedMessage` (fields are `pub(crate)`).
- **UniFFI boundary:** exported are `core_version`, `max_url_bytes`, `max_push_url_bytes`, `extract_shareable_url` (returns a plain `String`, sender-side only) and, from M1, the **sending** phone client: `Phone` (`inspect_pairing`, `begin_pairing(qr, confirm_group_change)`, list/forget PCs, rename, `send_url`, `refresh`), `Pairing` (code, wait, cancel), the `StateStorage` callback and `PhoneError` (UI text + a stable code string). The phone can't receive or open anything in M1. `VerifiedUrl`, `Inbox`, `UrlOpener`, `SystemOpener`, `OpenApproval`, `PendingOpen` and `RejectReason` are not exported; `scripts/build-android.sh` fails the build if they ever appear in the generated Kotlin.
- **No other process launch path:** the `open` crate and `tauri-plugin-opener`/`tauri-plugin-shell` are banned in `deny.toml`; CI also fails if `cargo tree -i open` finds it. `clippy.toml` disallows `std::process::Command::new` everywhere except the audited `opener::platform` module. The Tauri webview: strict CSP, bundled assets only, `withGlobalTauri` exposes only `invoke`, and **each window gets only its own commands** (`desktop/capabilities/`): the Pair a device window its `pair2_*` commands (`pair2_cancel` also closes the window, so the page needs no `core:window` permission; `scripts/gates.sh` refuses any `core:` permission); the devices window `devices_list/device_forget/settings_get/settings_set_no_prompt/settings_set_diagnostics/settings_set_theme/open_pair_window`; the confirm window `pending_list/pending_decide`. No window gets `shell`/`opener`/fs permissions, and no command takes a URL: `pending_decide(id, open)` acts on a link the core already verified and holds. Device names are set with `textContent` and `<bdi>` (AUTH-14).
- **The system opener itself:** re-runs the URL policy and requires the canonical string to be a fixed point, then makes exactly one launch: Windows `ShellExecuteW(NULL, L"open", canon, NULL, NULL, SW_SHOWNORMAL)` (`lpParameters = NULL`); Linux `/usr/bin/xdg-open <canon>`; macOS `/usr/bin/open <canon>`. No shell, no fallback launcher, no retry. `canon` always starts with `http://`/`https://`, so it can't be parsed as an option.

## 3. Release gates
- **Encryption gate (ENV-16/17, D1): passed in M1.** HPKE landed (`envelope::ENCRYPTION_IMPLEMENTED = true`, and the crate refuses to compile if it is set back to `false`). The M0 `insecure-preview` feature, its labels and its refusal of no-prompt mode are retired; artifacts are **release-profile** builds. `scripts/gates.sh` keeps a positive control (release build of core + desktop must succeed) and checks the preview feature is gone.
- **Test harness gate:** the `test-util` feature (fake clock, seeded RNG, deterministic keys, spy opener, fake peer, phone test hooks) has `compile_error!` under the release profile and under `VOIDWIRE_SHIPPING_BUILD=1` (set by `scripts/build-*.sh` and CI for every artifact). `scripts/gates.sh --artifacts` scans dist/ (APK .so, deb contents, binaries, and since N2 the **unpacked** NSIS payload and AppImage squashfs) for harness markers.
- **No-prompt default (open-notice toast removed 10-25-2026):** With revocation per link (§6.2 REV-06: Forget refuses the peer at once, with no group gap since message format 2), no-prompt is the **default**: `OpenMode::default()` is `OpenImmediately`, a fresh PC state starts with no-prompt on, and links from paired devices open without a question. Desktop open notifications were removed in M1.2 (10-25-2026) because OS notification centers log toast payloads to disk (`wpndatabase.db` on Windows). **"Ask before opening"** stays as a desktop setting (off by default) that restores the "Open link?" window. Saved state keeps the user's choice (an M1 state that stored "ask" stays "ask"; M1 can't tell an untouched default from an explicit choice, so it is treated as explicit). What still holds in both modes, with tests: an `OpenApproval` is minted only by `deliver` (no-prompt) after `Inbox::receive` fully verified the message, or by `PendingOpen::confirm`; the pairing re-check right before the open refuses a device removed between verification and open (`default_mode_opens_without_prompt_via_deliver`, `ask_before_opening_mode_waits_for_confirm`, `forgotten_between_verify_and_open_is_refused_in_both_modes`, plus the e2e tests). Gate `default-no-prompt-ask-setting` checks the default and that confirm mode and the re-check are still there. The rest of TEST-PLAN §10 (all P0s on the RC, fuzzing, the per-link revocation tests passing) still gates the v1 public release.
- **Signing:** M1 test builds are **not store-signed**. The APK is signed with a local development key kept outside the repo (`~/.voidwire/` on the build box); the Windows installer is unsigned (SmartScreen warns). Release signing keys stay in CI secrets later; this box never holds them.

## 3a. Human-in-the-loop surfaces (QA M1)
The core invariant is about the *receiving* side, but a paired phone that sends without its owner is just as bad in no-prompt mode. M1 closes the sender-side and prompt-side gaps QA found:
- **Android share target (QA M1 High, fixed):** `ShareActivity` is exported (it must be, to appear in the share sheet), so any app could start it with an arbitrary http(s) URL, and with exactly one PC paired it used to send on launch. It now never sends on its own: no send from `onCreate`, `onNewIntent`, restored state or intent delivery; only a tap on **Send to <PC>** that happens while the activity is resumed with window focus, ≥ 500 ms after the content appeared, and not through an overlay (`filterTouchesWhenObscured` + obscured-flag check). Re-delivered intents are ignored. One tap sends once. PROTOCOL.md §9.4; tests `ShareActivityTest` (Robolectric): programmatic launch, repeated/new intents, backgrounded intent and restored state never send; an explicit tap after the delay sends exactly once. **QA re-check L1:** obscured touches also re-arm the delay, a press must start after arming, and Android 12+ hides other apps' overlays over the share screen (`setHideOverlayWindows`, permission `HIDE_OVERLAY_WINDOWS`). *Residual:* a malicious app with accessibility-service rights can tap for the user; that is same-device malware (§6.5). On Android 8-11 an overlay that vanishes without the user touching our window in between can't be detected (the delay and press-after-arming rule still apply).
- **Different device group (OQ-9 / PAIR-11, fixed on the phone; bypass closed in the QA re-check):** see §6.6.
- **App crash on launch (QA re-check C1, fixed):** the shipped APK aborted in iroh's DNS resolver because the JNI context was never installed (a denial of service on the user's own device, not a security bypass). Now installed by `NativeInit` before `Phone()`, `Phone()` errors instead of aborting without it, the Android library unwinds on panic (UniFFI turns a panic into an exception), and an on-device smoke test covers launch, the share sheet and building `Phone()`.
- **Desktop confirm window (fixed):** never focused, never always-on-top (taskbar flash instead), Open disabled for 1 s after any change, in-place list updates, trusted clicks only; prompts expire after 2 min (`PromptExpired`), unknown ids are `NoSuchPrompt`. PROTOCOL.md §9.3.

## 4. Check ordering rationale
Cheap checks that need no secrets run first and reject strangers without parsing (`NotPaired`). Signature verification precedes anything stateful, so a forger can't consume a real device's rate budget or fill the replay cache. The per-device budget is charged for every **authenticated** message, valid or not (a compromised device can't spin CPU with bad messages), before the global budget (a flooder's rejects don't starve other devices). The URL policy is last and is repeated at the opener.

## 5. Parties and what they see
(From PLAN §3, unchanged.)

| Party | Can see | Cannot see |
|---|---|---|
| LAN observer | That two devices talk, packet sizes | URLs, keys |
| Relay | IPs, EndpointIds that relay through it, timing, padded sizes; from M2 also opaque group-log mailbox ids (unlinkable, per epoch), padded record sizes and which IPs read/append them | URLs, device names, group membership, plaintext group-log ops |
| Push gateway | Sender IP, push token (in memory), timing, padded size | URLs, sender identity, group |
| Apple / Google | That the phone got a push at time T, padded size | URL, sender |
| Paired device in your group | Everything you send it | n/a |

**M1:** URLs are HPKE-encrypted inside QUIC/TLS 1.3 on the LAN. A LAN observer also sees mDNS announcements of the PC (service `voidwire`, EndpointId, addresses), so it can tell a Voidwire PC is on the network.

## 6. Known weak points and residual risks
1. **A compromised paired device is fully trusted** (PLAN §3 #1). It can open arbitrary http(s) pages (drive-by risk) and, in v1, add devices. Mitigations: allow-list, rate limits (burst 5), "Ask before opening" (shows the punycode host and device name first; **off by default since 10-11-2026**), and two-click "Forget" in Paired devices. *(Note: the M1.1 desktop OS notification "Opened <host> from <device name>" was removed in M1.2 on 10-25-2026 because OS notification centers such as Windows Action Center `wpndatabase.db` log toast payloads to disk, violating the no-logs rule; see PROTOCOL.md §9.5.)*
2. **Revocation (REV-06): per link, no group gap since message format 2.** There is no group log, `SYNC`/`OPS` or relay group mailbox any more. A link joins exactly two devices, and "Forget" erases that link on the device at once; from then on that device refuses the peer at the app ALPN (`NotPaired`, before any frame is read). It then sends the signed unpair op to the peer in the background, best effort (live, or into the peer's pairing inbox), so the other side can erase its half too. No third device needs to hear about it, so the M1/M2 gap (a PC that missed a removal and hears only from the removed device) no longer exists. *Residual:* until the unpair op arrives, the other side still lists the link and may try to send on it; the forgetting device refuses everything it sends.
3. **Replay after restart (ENV-05): closed in M1.** The seen-ID store is fsync'd before an open is allowed and re-loaded at startup (tested across a PC restart in `e2e_net`). QA M1 hardening: `seen.bin` is `0600` in a private dir (Windows: protected per-user DACL), records are length-prefixed and checksummed with torn-tail recovery, and a **missing or corrupt** file on an initialised install fails closed: for one replay window after startup only messages timestamped after startup are accepted (PROTOCOL.md §5). **QA re-check L2:** a high-water mark in `state.bin` (newest durable `seen.bin` record + latest expiry) also catches a file truncated at a record boundary, cut to its header, or with its last record changed; those fail closed too. *Residual:* someone who can rewrite both `seen.bin` and `state.bin` (same user, write access to the 0700/ACL'd data dir) can still roll both back; in M1 a replay also needs a captured envelope from a paired phone. **QA final I1, accepted and out of scope:** the high-water mark is an *optional, unauthenticated* trailing section of `state.bin` (no MAC, no "must be present once written" flag), so the same local writer can simply delete it (or both files) and the check is skipped. This is deliberate: local write access to the data dir already means full compromise of the PC side (that writer can replace `state.bin`'s identity key and pairings, or the binary itself), so authenticating the mark would add no protection against anyone it is meant to stop. The mark only exists to catch accidental truncation/corruption and partial tampering that leaves `state.bin` intact. **Recovery** (L4): the guard lifts by itself after 20 minutes and new links work meanwhile; an unreadable `seen.bin` stops the node until it's deleted (documented in the test sheet). Refusals and the guard are logged to `voidwire.log` in the data dir (no links).
4a. **DNS rebinding (accepted risk, M1):** host names are not resolved by the URL policy, so a public name resolving to loopback or a LAN address (`127.0.0.1.nip.io`, a rebinding DNS server) passes. Resolving at check time is useless (the browser resolves again). Exposure equals clicking the link on the PC; mitigated by paired-only senders, and by "Ask before opening" (host shown first) for users who turn it on. Pinned by a test.
4. **Local/private hosts (OQ-8, decided):** loopback, link-local and unspecified hosts are rejected in every spelling; RFC 1918 and IPv6 ULA hosts are **allowed**, so a compromised paired device could still make the PC open (GET) a home-LAN admin page. Accepted for v1 (home-LAN links are a real use case); with no-prompt as the default since 10-11-2026 such a link opens without a question unless "Ask before opening" is on. Revisit as a user setting in v2.
5a. **Pre-decryption CPU cost (D13 / OQ-19): closed in M1.** A cheap bucket keyed on the authenticated `transport_peer` runs before HPKE open and signature verification (`RateLimitedPeer`); non-members are refused at the app ALPN before any frame is read.
5b. **LAN exposure (M1):** the PC listens on UDP (QUIC) on the LAN. The Windows installer opens the firewall for `voidwire.exe`, inbound UDP, **Private profile only**, from the **local subnet only** (`remoteip=localsubnet`, gate `nsis-firewall-private`), and removes the rule on uninstall; on Public networks Windows keeps it closed. Only paired peers (a device with a pairing link here) get past the TLS handshake on the app ALPN; the pairing ALPN only accepts frames while a QR is shown.
5. **Metadata** (relay sees EndpointIds/IPs), **no forward secrecy on the push path**, **same-user malware**, **supply chain**: as in PLAN §3 #3–#6. Release signing keys stay in CI secrets; this box never holds them.
6. **Hostile QR (OQ-9 / PAIR-11).** A phone shown an attacker's QR would pair with the attacker's PC. Since message format 2 that adds **one new link** and nothing else: there are no groups, so no existing link is merged, moved or redirected, and the attacker's PC gets no path to the user's other devices. The PC's name from the QR's `n=` is verified against its signed cert (`SenderMismatch` on a forged name), and the user types the SAS on the PC. Links still only go to a PC the user taps in the share screen. *Residual (accepted 10-31-2026):* the M1 "different device group" and "Another PC with this name?" warnings went with the group roster (`GroupChangeNotConfirmed` was deleted; its wire code 45 stays reserved), so a user who pairs with a hostile PC that copied a real PC's name sees two PCs with that name and could tap the wrong one. **PC side: not applicable**: the PC never scans a QR.
7a. **Pairing state at rest (M4.1).** The pairings section of the state file is MACed with a key derived from the device identity secret and per-pairing epoch secrets are sealed inside it, so a damaged or partly edited section stops the app instead of loading different peers. *Residual:* as for the high-water mark (3.), a local writer who can replace the whole file can replace the identity too; the MAC catches corruption and partial tampering, not a full rewrite. Downgrade to 0.4.x is refused by the old app, never silently half-loaded: the 0.4.x PC app stops with a storage error, and the 0.4.x Android app treats the file as unreadable and deletes it (re-pair needed either way).
7b. **Relay supervisor (M4.1).** A dead relay is parked after 30 s and probed with one plain TCP connection on a doubling schedule (30 s to 30 min). The probe carries no data, so the relay operator (and the network) sees only a TCP connect from the device's IP, as with any relay connect. *Residuals:* a relay whose port answers but whose relay service is broken passes the probe, so each such unpark lets iroh retry for another 30 s before it is parked again; iroh 1.3 keeps redialing a removed home relay (about 165-180 attempts an hour instead of about 1,300-1,450; TEST-PLAN §13 has the numbers), which costs battery but leaks nothing new. The lighter background check (experiment, off) drops QUIC address discovery in background, which can make direct connections slower to form behind some NATs; it ships off until measured on hardware.
7. **External crypto review** of pairing, envelope and the pairing links is required before public launch.

## 7. Data inventory (M1.1, privacy-first rule of 10-11-2026)

Rule: nothing is logged or kept as history unless the user turns it on; store as little as possible; convenience features are opt-in. Every byte either app writes to disk is listed here. `scripts/gates.sh` (privacy-no-default-logs) fails CI if a new file writer appears in the desktop crate outside `diag.rs`/`node.rs`, if the log write is no longer gated on Diagnostics, if Android SharedPreferences are used outside `RecentSends.kt`/`UiPrefs.kt` (or Remember last PC writes while off), or if a desktop webview stops being incognito.

### 7.1 Desktop (Windows `%APPDATA%\app.voidwire.desktop`, Linux `~/.local/share/app.voidwire.desktop`; `VOIDWIRE_DATA_DIR` overrides)

| File | Contents | When | Protection / lifetime |
|---|---|---|---|
| `state.bin` | Device keys (Ed25519 identity, HPKE), the "Ask before opening" flag, the replay high-water mark, the pairings (peer ids and names, relay URL, sealed per-pairing secrets, pairing logs) and saved relays, MACed | Always (needed to work) | DPAPI-sealed on Windows (user scope), 0600 on Linux; until uninstall |
| `seen.bin` | Replay cache: sender id, message id, timestamps. **No URLs, no hosts** | Always | Entries expire after ~20 min |
| `instance.lock` | Empty; an OS file lock so only one copy runs | Always | Released on exit |
| `theme` | `dark` or `light`: the Settings → Appearance → Theme choice (round 2) | Only when the user picks Dark or Light; System (the default) stores nothing | Deleted when set back to System |
| `diagnostics.on` | Empty marker = the Diagnostics switch | Only when the user turns Diagnostics on | Deleted when turned off |
| `voidwire.log`, `voidwire.log.old` | Start-up, network errors, refused links as *device + reason* (never the link or host) | **Only with Diagnostics on** (off by default) | Rotated at 256 KB; deleted when Diagnostics is turned off |
| `crash-<ms>.txt` | Panic message + location + backtrace (no link: the panic hook never formats a URL) | **Only with Diagnostics on** | At most 5, 0600; deleted when Diagnostics is turned off |
| WebView2 / WebKitGTK profile (`%LOCALAPPDATA%\app.voidwire.desktop`) | Engine runtime files only: every window is built with `.incognito(true)`, so no cookies, localStorage, IndexedDB or HTTP cache are kept (the pages use none anyway) | Engine-managed | Removed by the uninstaller ("Remove all Voidwire data", default on) |

Not on disk: pending "Open link?" items (memory only, dropped after 2 min), pairing secrets/QRs (memory only, one live at a time, revoked on refresh/pause/close), "Listening" status. Outside our files: the installer's uninstall registry key and the Private-profile firewall rule (removed on uninstall). No OS notifications are emitted (removed in M1.2 so OS notification centers never log opened hosts or device names to disk).

### 7.2 Android (app-private storage, excluded from backup)

| File | Contents | When | Protection / lifetime |
|---|---|---|---|
| `files/no_backup/phone-state.bin` | Keys, this phone's name, paired PCs (ids, names, cached LAN addresses), group ops; since M4.1 also the pairings and saved relays (MACed section, sealed per-pairing secrets) | Always | AES-GCM with the Android Keystore key `voidwire-state-v1`; an unreadable file is deleted (not kept aside) |
| `shared_prefs/recent_sends.xml` | Time, host (never the full link), PC name and result of the last 20 sends | **Only when "Keep recent sends" is on** (Settings, off by default) | Turning it off deletes the file; at every start, if it is off, the file is deleted (this also wipes M1 testers' history) |
| `shared_prefs/share.xml` | The flag and `last_pc` (the id of the PC last sent to) | **Only when "Remember last PC" is on** (Settings, off by default; round 2). Off: the share sheet lists PCs A–Z and nothing is written | Turning it off deletes the file; at every start, if it is off, the file is deleted (this also wipes the file M1 wrote without asking) |
| `shared_prefs/ui.xml` | `theme_mode` = `dark` or `light` (Settings → Appearance → Theme) | Only when the user picks Dark or Light; System (the default) stores nothing | Deleted when set back to System |

Not on disk: the shared URL (memory only, the activity finishes after sending), Check results ("Reachable"), camera frames (analysed in memory for the QR only).
