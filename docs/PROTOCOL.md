# voidwire protocol, draft v1 (M1)

*`voidwire` is the fixed protocol name (§1.1); the product is Voidwire. Status: draft for the external crypto review (PLAN §3 #7). M1 (Oct 10, 2026): HPKE envelope, LAN transport, network pairing, signed group log. Sources: THREAT-MODEL.md, TEST-PLAN.md, and the architecture decisions in §8 below. Normative words: MUST, MUST NOT, SHOULD.*

Implementation status per section: **[M0]** implemented and tested in `core`; **[shaped]** types/constants exist in `core`, behavior lands in the stated milestone; **[M1+]** spec only.

## 1. Identities and keys
- **Device identity [M0]:** Ed25519 key pair. The public key is the `DeviceId` and (from M1) the iroh EndpointId. `DeviceId::from_bytes` MUST reject non-canonical encodings and **weak (small-order) keys** (`RejectReason::BadSignature`); every `DeviceId` in the program is therefore a usable, strong key.
- **Receive key [M1]:** X25519, carried in a **signed device certificate** (`voidwire/v1/device-cert\0`: device id, receive key, platform, name, signed by the identity key) exchanged during pairing and stored in the group log. Rotation (monthly, grace period) lands in M4.
- **Group [shaped]:** `GroupId` (32 bytes; M4: hash of the genesis op). A roster lists member `DeviceId`s with a role (`owner`/`member`/`guest`; every v1 device is `owner`) and a removed flag (tombstone).
- **Storage [M1]:** one state blob per app (identity + receive secret keys, flags, group log), written atomically with mode 0600. Windows: DPAPI (current user). Android: AES-256-GCM under a non-exportable AndroidKeyStore key, in `noBackupFilesDir`. Linux: file permissions only in M1 (Secret Service: M2). Secrets are zeroized on drop.

### 1.1 Protocol name (fixed) [M0]
The protocol name is **`voidwire`**, version **1**. It is **not** branding and MUST NOT change when the product is renamed (D9). It appears in:
- the pairing QR URI scheme: `voidwire:pair?v=1&…` (§6);
- every domain-separation tag: `voidwire/v1/message\0`, `voidwire/v1/pair-id\0`, `voidwire/v1/pair-proof\0`, `voidwire/v1/sas\0`, `voidwire/v1/pair-transcript\0`, `voidwire/v1/replay\0`, `voidwire/v1/log-op\0`, `voidwire/v1/device-cert\0`, `voidwire/v1/envelope\0`, `voidwire/v1/log-sig\0`;
- the transport labels: ALPNs `voidwire/v1/pair` and `voidwire/v1/app`, TLS exporter label `voidwire/v1/pair-exporter`, mDNS service `voidwire`;
- the wire magic `VW 01 00` (§4).

History: the M0 drafts used an early working name as the protocol name; it was changed **once**, to `voidwire`, on Oct 10, 2026 before any build shipped (no deployed peers to stay compatible with). From now on the protocol name is fixed even if the product is renamed again.

Single source: `core/src/protocol.rs`. Unit tests assert every tag in `DOMAIN_TAGS` and `TRANSPORT_LABELS` starts with `<PROTOCOL_NAME>/v<PROTOCOL_VERSION>/`, and the list is **checked against the source**: a test scans `core/src/**` recursively for every `voidwire/v1/…` literal and fails if one is missing from the lists (QA: "generate or test the tag list"). Public, renameable identity (app name, bundle/package IDs, binary name, env-var prefix, repo URL, publisher) lives in `branding.properties` (README "Renaming").

## 2. Transport [M1]
iroh 1.3 (QUIC/TLS 1.3, dial by EndpointId; the EndpointId **is** the device identity key, so `EndpointId == DeviceId`). M1 is **LAN only**: relays disabled (`RelayMode::Disabled`), n0 DNS/pkarr discovery off. Discovery: local mDNS (service `voidwire`; the PC advertises, the phone only browses) **plus** direct addresses the PC puts in the QR (`a=` hints, up to 6) and that the phone stores per PC; the PC prefers UDP port 48484 (falls back to any). Framing on a bidirectional stream: `type u8 || len u32 BE || payload`, with a per-type cap checked **before** the payload is read (unknown types: cap 0). Frames: `HELLO 1, INVITER_CERT 2, PROOF 3, PROOF_OK 4, WELCOME 5` on the pairing ALPN; `SYNC 0x10, OPS 0x11, SEND 0x12, RESULT 0x13 (u16 code, outcome 1=opened / 2=prompted), ERROR 0x7F (u16 reject code)` on the app ALPN. A refusal closes the connection with application code `0x100 + RejectReason::code()`. **Address fallback [M1, QA]:** the phone first dials the PC's cached/QR addresses; if that fails (dead address, or a poisoned one that answers with the wrong TLS identity), it falls back to a fresh mDNS lookup, still dialling by device id so the TLS identity check applies, and writes whichever path worked back to its cache. **[QA re-check L3]** In a cold process (the share sheet) mDNS has no answers yet, so the fallback first **waits up to 2 s** for an mDNS answer for that PC and dials the addresses found. Because a wrong-identity address stays in iroh's path set and can win the race with a fast TLS failure, it redials up to 8 times within 1.5 s (each dial is a full identity check; slow failures aren't retried). Relay URLs from the roster come back in M2. A receiver MUST accept app-ALPN connections only from EndpointIds that are **active** roster members, and MUST pass the authenticated peer id into `Inbox::receive(transport_peer, bytes, now)` of the app's single `Inbox` (which owns the roster, §5). Pairing uses a separate ALPN that accepts pairing frames only.

## 3. Envelope
- **Encryption [M1, done]:** HPKE (RFC 9180) base mode, DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 (rust-hpke), sealed to the recipient's receive key from its signed cert. No other suite, no fallback. `envelope = header(4) || enc(32) || ciphertext`, `header = 'V' 'W' 01 01` (version, suite) and is the HPKE `aad`; `info = "voidwire/v1/envelope\0" || recipient DeviceId`. The plaintext is the **signed** message of §4 (inner signature), padded as below. `ENCRYPTION_IMPLEMENTED = true`; the crate refuses to compile if it is set back to `false`, and the M0 `insecure-preview` feature and its labels are retired, so artifacts are **release-profile builds**. HPKE base mode is *not* authentication; authentication is the inner signature plus the transport binding (§4, §5 step 3).
- **Plaintext framing [M0]:** `u32 BE body_len || body || zero padding` to the smallest bucket in **512, 1024, 2048, 4096, 8192, 8448** bytes. The last bucket is "8 KiB + header" so an 8 KiB URL fits (8192 + 222-byte header/signature + 4-byte prefix = 8418). Receivers MUST reject: a length that is not a bucket, `body_len` that would fit a smaller bucket, non-zero padding, anything above 8448 bytes (`MalformedFrame`).

## 4. Message body [M0]
All integers big-endian; total header 158 bytes + URL + 64-byte signature.

| Field | Bytes | Notes |
|---|---|---|
| magic | 4 | `'V' 'W' version reserved` = `56 57 01 00`. Unknown version → `UnsupportedVersion`; reserved ≠ 0 → `MalformedFrame` |
| group | 32 | `GroupId` |
| sender | 32 | sender `DeviceId` (must parse as a strong key) |
| recipient | 32 | recipient `DeviceId` |
| log_head | 32 | sender's group-log head (§7) |
| msg_id | 16 | 128-bit random |
| timestamp | 8 | sender wall clock, Unix ms (UTC) |
| url_len | 2 | |
| url | url_len | UTF-8 (invalid UTF-8 → `MalformedFrame`) |
| signature | 64 | Ed25519 over `"voidwire/v1/message\0" || every preceding byte` |

Decoding is strict (exact length, no trailing bytes). Verification uses `verify_strict`. The signature covers every field including magic/version (AUTH-09).

## 5. Receive pipeline (normative order) [M0]
`Inbox::receive(transport_peer, envelope, now)` is the **only** producer of `VerifiedUrl`. The `Inbox` **owns** the app's roster (`Inbox::new(roster, config)`; roster changes only through `Inbox::add_paired_device(ConfirmedPairing)` and `Inbox::forget_device`), so verification can't be pointed at another device list; each `VerifiedUrl` is tagged with the inbox that minted it (D2, AUTH-17). `InboxConfig` is validated against floors/ceilings in `limits.rs` (burst and per-minute 1..=10 000; timestamp window 30 s..=600 s, never wider than the replay retention is sized for; replay cache 1..=1 000 000 entries); out-of-range values are rejected (`InboxConfigError`), never clamped silently (D5, FC-04).

1. `transport_peer` is an active roster member, else `NotInRoster` / `Removed` (nothing parsed); peer ≠ self (`FromSelf`).
2. Envelope size/padding (§3), strict decode (§4).
3. `sender == transport_peer`, else `SenderMismatch`.
4. `group` == ours (`WrongGroup`), `recipient` == us (`WrongRecipient`).
5. `verify_strict` under the sender key (`BadSignature`).
6. Per-device rate limit (`RateLimitedDevice`). Every authenticated message counts, valid or not (RL-06); keyed only by the authenticated sender (RL-07).
7. Sender's `log_head` (§7): behind ours → `StaleGroupHead`; unknown → `UnknownGroupHead` (sync first).
8. Timestamp: `|ts − now.wall| ≤ 600 000 ms` **inclusive**; older → `StaleTimestamp`, newer → `FutureTimestamp`. Overflow-safe for 0 and `u64::MAX`.
9. Replay cache keyed on `SHA-256("voidwire/v1/replay\0" || sender || msg_id)[..16]` → `Replay`; full → `CacheFull` (fail closed, never evict in-window ids).
10. Global rate limit (`RateLimitedGlobal`). Checked after per-device so a flooder's rejects don't drain it (RL-05).
11. URL policy (§9.1).

**[M1, done] Pre-decryption per-device budget (D13 / OQ-19).** Between steps 1 and 2 a cheap token bucket keyed on the authenticated `transport_peer` (`InboxConfig::pre_decrypt`) is charged before HPKE open and signature verification (`RateLimitedPeer`), so a compromised member can't make the PC spend unbounded CPU. Strangers never get that far: the PC refuses non-members at the app ALPN after the TLS handshake, before reading a frame.

**[M1, done] Replay cache persistence (ENV-05).** `replay::FileSeenIdStore`: each accepted message's replay key is appended and **fsync'd before the open is allowed**; on startup the file is re-read (in-window entries only) and compacted. **Hardening [M1, QA]:** `seen.bin` format 2 is length-prefixed records, each with a SHA-256-based check; a torn tail (crash mid-append) is dropped and the file realigned, damage before the tail is `Corrupt`. The file is created `0600` inside a private data dir (`0700` on Unix; a protected current-user + SYSTEM DACL on Windows). **High-water mark [M1, QA re-check L2]:** the PC also keeps, in `state.bin` (an optional trailing section), the newest durable record of `seen.bin` and the latest expiry ever written, re-saved whenever they move (after the fsync'd append, before the sender gets its answer; also right after every rewrite). At startup a `seen.bin` that no longer contains that record (truncated at a record boundary, cut to the header, or its last record damaged or replaced) is `Corrupt`, unless every record ever written has already expired. **Fail closed:** if `seen.bin` is missing or corrupt on an already-initialised install (`StoreHealth::Missing`/`Corrupt`; a fresh install is `FirstRun`), then for one replay window after startup only messages timestamped **after startup** are accepted (`ReplayStartupGuard`), so deleting or damaging the file can't reopen replay. `PcNode::replay_cache_health()` exposes the result; the desktop logs it to `<data dir>/voidwire.log` and says so in the tray tooltip, and the phone shows "The PC just restarted its replay protection…" for `replay_startup_guard` (L4). **Recovery:** none needed for the guard (it lifts after 20 min; new links go through meanwhile). If `seen.bin` can't be read at all the node doesn't start (tooltip "not listening (replay cache: …)"): quit, delete `seen.bin` in the data dir (Windows `%APPDATA%\app.voidwire.desktop`), start again; that restarts with the guard on. Tested across restart (`e2e_net` restart test), kill mid-write, truncation and deletion.

**[M1, done] One Inbox per process (R1).** A second live `Inbox` in the same process fails to construct (`SecondInbox`); in-process code is outside the guarantee (THREAT-MODEL §2). The process-wide slot is released when the `Inbox` holding it is dropped, so a `PcNode` can be shut down and started again in-process (QA M1); there is still at most one live `Inbox` at a time (`tests/one_inbox_per_process.rs`).

Clocks are injected: `Now { wall: UnixMillis, mono: MonoMillis }`. Wall time is used only for comparing with other devices (timestamps, QR `exp`); every local timer (pairing expiry, SAS timeout, rate-limit refill, cache eviction) uses the monotonic clock. Core never reads the system clock except in `time::SystemClock`.

Reorder (ENV-07): no sequence numbers; each message is accepted at most once regardless of order.

## 6. Pairing (QR + SAS)
1. **[M0]** Inviter issues a 128-bit single-use secret `s` (RNG self-test: all-zero or repeated output is refused). QR: `voidwire:pair?v=1&id=<inviter hex>&r=<relay, form-encoded>&g=<group hex>&s=<hex>&exp=<unix ms>`. The scanner's parser is strict: required `v,id,g,s,exp`; duplicate params rejected; unknown `v` → `UnsupportedVersion`; `now.wall ≥ exp` → `PairingSecretExpired`. `exp` is informational; the inviter enforces expiry on its own monotonic clock.
2. **[M1, done]** QR (M1): adds `a=<ip:port>` direct-address hints (≤ 6). Joiner dials `id` on the pairing ALPN; the QR id authenticates the inviter via iroh's TLS identity. Frames: `HELLO` (secret_id; the PC rejects unknown/used/expired here and **consumes** the secret), `INVITER_CERT`, `PROOF` (request + joiner cert), `PROOF_OK`, then `WELCOME` (the signed group log) once the user typed the code. The PC shows one QR at a time; closing the window cancels it (`PairingCancelled`). **[M1.1] Auto-refresh:** 10 s before a QR expires the PC mints a new one (its own 120 s TTL); the replaced secret keeps a grace of `QR_REPLACED_GRACE_MS` (10 s, never past its own expiry) so a phone that scanned it just before still pairs (`QrSchedule`, `PcNode::pair_status`). Refreshing stops after 10 minutes (the window then shows "Pairing paused" (Show a new code)), and while the window is hidden (it stops polling). Hiding or minimizing never revokes the live QR; only Cancel, closing the window, a new code, or expiry end it. A revoked or replaced secret answers `PairingSecretExpired`; `PairingSecretUsed` means a proof was already checked against it.
3. **[M0]** Joiner sends `PairingRequest { secret_id, joiner, joiner_name, proof }`, where `secret_id = SHA-256("voidwire/v1/pair-id\0"||s)[..8]` and `proof = HMAC-SHA256(s, "voidwire/v1/pair-proof\0" || T)`. Transcript `T = "voidwire/v1/pair-transcript\0" || group || inviter || joiner || u64 len || joiner_name || u64 len || handshake`; M1: `handshake = exporter(32, label "voidwire/v1/pair-exporter", context = secret_id) || u16 len || inviter cert || u16 len || joiner cert`, so a recorded transcript can't be replayed on another connection (PAIR-03) and the certs are bound. The joiner cert's id and name must match the request (`MalformedFrame`).
4. **[M0]** Inviter: the secret is **consumed by the first attempt of any kind** (valid, bad proof, expired). Hard expiry 120 s after issue; expired at `≥ 120 s` (PAIR-05). Errors: `PairingSecretUnknown`, `PairingSecretUsed`, `PairingSecretExpired`, `PairingHmacBad`. Device names: 1–64 bytes, no control chars (M1 adds bidi isolation in UI).
5. **[M0]** SAS = `HKDF-SHA256(salt="voidwire/v1/sas\0", ikm=s, info=T)` → 8 bytes → `mod 10^6`, shown as 6 digits on the **joiner**. The inviter's confirm screen shows the **joining device's name** and the user must **type** the 6-digit code (not a bare tap). One try; mismatch → `SasRejected`; more than 120 s after the proof → `SasTimeout`. Only `PairingGrant::confirm_typed_code` creates a `ConfirmedPairing`, and only `Roster::add_paired_device` consumes one.
6. **[M1, done]** The inviter appends a signed `add_device` op (§7) and sends the log in `WELCOME`.
7. **[M1, done] Different-group warning (OQ-9 / PAIR-11).** The QR also carries `n=<inviter device name>` (form-encoded, same rules as device names). It is unauthenticated in the QR but is **checked against the inviter's signed cert** during pairing; a mismatch is `SenderMismatch`. Before any network traffic the joiner calls `inspect_pairing(qr)` (core `PhoneClient::inspect_invite`), which reports the PC's name and whether this QR **joins a different device group** than the ones the phone is already a member of (re-pairing within a group it's in needs no warning). **"Same group" is decided from authenticated identity, not the QR's `g=`** (QA M1 re-check: `g=` is printed in every QR and a fake PC can reuse it): the QR's inviter id must be the **owner or a member of a signed group log the phone already holds**, with the same group id. That id is the PC's endpoint key, which the QUIC/TLS handshake proves; the decision is repeated after the PC's signed certificate arrives (before the secret proof is sent) and again against the signed log in the welcome (before anything is stored). `inspect_pairing` also reports `duplicate_name` when a *different* paired PC already has that name ("two Home PCs"); it needs the same confirmation. `begin_pairing(qr, confirm_group_change)` refuses with `GroupChangeNotConfirmed` before dialling unless the caller passes `true`; the Android app passes `true` only after the user taps **Join** in "This will join a different device group (named X)", where Cancel is the default (back, outside tap and the primary button all cancel). Rosters are never merged. **PC side: not applicable in M1**: the PC never scans QR codes (it only shows them), so it can't be steered into another group; revisit if PC-side joining is added.

## 7. Group log and revocation
- **[shaped, M0]** Each roster change advances a hash-chained head: `head' = SHA-256("voidwire/v1/log-op\0" || head || op || device)`. Receivers keep prior heads; a message whose `log_head` is a prior head is `StaleGroupHead`, an unknown head is `UnknownGroupHead` (M1: triggers sync, then retry).
- **Forget this device [M0 API, ships in M1 UI]:** `Inbox::forget_device` (→ `Roster::remove_device`) on the PC takes effect locally and immediately; the device becomes a `Removed` tombstone. `opener::deliver` and `PendingOpen::confirm` re-check membership immediately before opening (REV-04).
- **Signed log [M1, done]:** the PC (group owner) signs every op: `SignedOp = 'V' 'W' 01 'L' || kind(genesis 1 / add 2 / remove 3) || subject || name || cert || prev head || head || Ed25519("voidwire/v1/log-sig\0" || …)`. Members keep a `GroupReplica`: they verify the author, the genesis and the head chain, refuse rollback and forks, cap the log at 512 ops. Every connection starts with `SYNC(head)`; if heads differ the PC answers `OPS` with the full log. Each message carries the sender's head (§4).
- **Remove propagation [M1, done; pull-based relay mailbox M2]:** "Forget this device" on the PC appends a signed `remove_device` op, closes the device's open connections (`Removed`) and takes effect locally at once. Devices exchange `SYNC`/`OPS` **on every connect**, so the signed op reaches the removed phone, and every other member, **directly** the next time it connects; the phone's replica then reports `Removed` and the UI says so. There is **no per-device delivery tracking** (no acks, no retry queue; the M1 `pending_removal_deliveries` ack map was removed). Every message carries the sender's head (§4), so a removed device that withholds the op can't keep sending to a member that has heard of the removal from anyone. **M2** adds a relay mailbox that devices *pull* from (§7.1). Without a relay (LAN only, or self-hosting turned off) behaviour stays exactly as in M1: peer sync plus local Forget.
- **M4:** full signed DAG (`genesis`, `add_device`, `remove_device`, `rename`, `set_relay`, `rotate_receive_key`), remove-wins.
- **Residual risk (REV-06): documented for alpha** (with no-prompt as the default; THREAT-MODEL §6.2). In M1 (and in M2 without a relay): a PC that is offline during a removal and afterwards hears **only** from the removed device (which withholds the op and presents an old head that the PC still considers current) keeps accepting it until any other member reaches it. Mitigations: direct op delivery on every connect, local "Forget this device" on the PC, and from M2 the pull-before-trust rule (§7.1 (e)), which closes most of the gap; what remains is listed there.

### 7.1 Pull-based revocation: relay group-log mailbox [removed]

*This design was never shipped and its relay store has been removed: the mailbox relay now serves only the signed config and the RAM-only per-device inboxes (`INBOX_PUT`/`INBOX_PULL`/`INBOX_ACK`). Frame types `0x01`–`0x05` are refused as malformed. The text below is kept as background only.*
The relay additionally holds the group's **latest signed group-log ops** and serves them to any device on (re)connect. A device must pull them before it accepts a URL from a peer it hasn't re-synced with (e). The relay is a dumb, append-only store; all verification is done by clients. The constraints below are what make this safe.

**(a) Opaque, unlinkable storage.** The relay never sees the group id, device ids, device keys or plaintext ops.
- **Group secret.** Each group has a 32-byte secret per **epoch** `e` (u32, starting at 0): `gs_0` is drawn from the OS RNG by the owner at genesis; every removal starts a new epoch `e+1` with a fresh random `gs_{e+1}`. `gs_e` never leaves the members' state files (zeroized in memory like the other secrets) and is never sent to the relay.
- **Derived values** (HKDF-SHA256, RFC 5869; `ikm = gs_e`; `ctx = "voidwire/v1" || group_id(32) || u32be(e)`; the group id is non-secret context only, the output is unlinkable because the ikm is secret):
  - mailbox id: `mbx_e = HKDF(salt = "voidwire/v1/mailbox-id\0", ikm = gs_e, info = ctx, L = 32)`
  - content key: `kenc_e = HKDF(salt = "voidwire/v1/mailbox-enc\0", ikm = gs_e, info = ctx, L = 32)`
  - write token: `wtok_e = HKDF(salt = "voidwire/v1/mailbox-write\0", ikm = gs_e, info = ctx, L = 32)`; the relay stores only `wver_e = SHA-256("voidwire/v1/mailbox-write-verifier\0" || wtok_e)`.
  - seal token (owner only): `stok_e = HKDF(salt = "voidwire/v1/mailbox-seal\0", ikm = owner_seal_root, info = ctx, L = 32)`, where `owner_seal_root` is a 32-byte secret that **never leaves the owner device** (state.bin); the relay stores `sver_e = SHA-256("voidwire/v1/mailbox-seal-verifier\0" || stok_e)`.
- **Records.** Each record is `XChaCha20-Poly1305(kenc_e, nonce = 24 random bytes, aad = "voidwire/v1/mailbox-rec\0" || mbx_e, plaintext = one or more SignedOps)`, padded to the §3 buckets before encryption so sizes don't reveal the op kind or member count. The relay sees `mbx_e`, record sizes, timing and the client IP, nothing else. *Residual metadata:* the IPs that read or append to the same mailbox, and when, let the relay guess that those connections belong to one group (the same class of metadata a relay already sees, THREAT-MODEL §5); it learns no ids, names or member count.
- **Who writes.** The author of every signed op (the owner in M1–M3) appends it to the current mailbox right after applying it locally; peers keep syncing directly as well.
- **Existing M1 groups.** They have no group secret yet. On the first M2 start the owner draws `gs_0` and an `owner_seal_root`, and distributes `gs_0` in a signed `rekey` op for epoch 0 (sealed to each member as below), delivered by peer sync.
- **New member.** `gs_e` and `e` for the **current** epoch go in `WELCOME` (§6 step 6), which is sent only after the typed code, on the inviter-authenticated pairing connection, and additionally HPKE-sealed (§3 suite) to the joiner's receive key from its cert (`info = "voidwire/v1/epoch-key\0" || group_id || u32be(e)`). A new member never gets older epoch secrets.
- **Rotation on removal.** The remove is followed in the signed log by a signed `rekey` op `{e+1, [(member_id, HPKE-seal(member receive key, gs_{e+1}, info as above))…]}` with an entry for **every remaining member and none for the removed one**. It travels like any other op (peer `SYNC`/`OPS` and the mailbox), so an offline member learns the new epoch from whichever it reaches first. A removed device **cannot read anything written in epoch `e+1` or later and can't derive `mbx_{e+1}`**; it still knows `gs_0..gs_e`, so it knows the **old** mailbox ids and can read their (old) contents, including its own removal.

**(b) Append-only.** Per mailbox the relay supports only `append(record)` and `read(from_index)`: no delete, no overwrite, no reordering of stored records. Clients read **all** records, drop anything that fails decryption, signature, author, genesis or head-chain checks (`GroupReplica`, §7 "Signed log"), and merge the rest; rollback and forks are refused as today. So a removed device (or anyone holding an old `gs`) can neither roll back nor wipe its removal; it can only append junk, which clients drop.

**(c) Quota, rate limit, epoch-bound writes.**
- Appends need `wtok_e` (bearer, over TLS; checked against `wver_e`, which is fixed by the mailbox's first append). The token changes with every epoch, so a removed device **can't write to the new mailbox at all**.
- Per-mailbox quota and rate limit (≤ 1 MiB and ≤ 512 records per mailbox, ≤ 8448-byte records, 20 appends/min burst 20), plus the relay's per-IP limits. Over-quota appends are refused; existing records are never evicted early.
- **Sealing the old mailbox.** The removal is written as **one relay request** that atomically (1) appends the remove + `rekey` record to `mbx_e` and **seals** it (presenting `stok_e`; after that `mbx_e` refuses all appends, so a removed device can't flood it afterwards), and (2) creates `mbx_{e+1}` with `wver_{e+1}`, `sver_{e+1}` and the same record. One sealing append per mailbox is exempt from the quota, so a removed device that filled `mbx_e` beforehand can't block the removal record. An offline member that only knows epoch `e` reads `mbx_e`, finds the `rekey` op, derives `mbx_{e+1}` and continues there (following seals forward).
- **The remover's write is the only ack:** the UI says **"Removed"** after that one relay round trip succeeds. If the relay can't be reached, the removal still takes effect locally and the UI says "Removed on this PC; your other devices learn it when they connect" (d). There is no retry queue and no per-device delivery tracking.
- **Retention: 180 days since last access**, where any read or append (including the sealing append) renews it. A mailbox nobody has read or written for 180 days is deleted whole (never record by record, so (b) still holds while it exists); a device that comes back after that finds nothing to pull and must re-pair. A device still pulling a sealed old mailbox keeps it alive, which costs the relay at most one full quota per epoch.

**(d) No relay.** With no relay configured (LAN only, or self-host turned off), behaviour is the same as M1: peer `SYNC`/`OPS` on every connect plus local Forget. Nothing waits for a relay.

**(e) Pull before trust.** A device that has been offline (app start, network change, or no successful pull for more than 10 minutes) must complete a pull of its current mailbox chain (following seals to the newest epoch) **before it accepts any URL from a peer it hasn't re-synced with since**; a peer sync alone doesn't count, because the peer may be the removed device withholding the op. This closes most of REV-06 even when the only peer the device hears from is the removed one: the remove op comes from the relay. **Residual risk:** the relay is unreachable, or an attacker blocks it (e.g. a hostile network, or the removed device's owner controlling the LAN uplink), or a malicious relay withholds the newest records (omission can't be detected without another fresh source). **Pull failure fails OPEN.** If the pull fails, the device accepts URLs on peer sync alone (M1 behaviour) and keeps retrying the pull in the background, so LAN use keeps working while the internet is down. To make that visible, each device records the time of its **last successful pull** (wall clock, in its state file), and Paired devices shows **"Couldn't check for removals since <time>"** whenever the last pull attempt failed (cleared by the next successful pull). The residual above is accepted for that window (THREAT-MODEL §6.2 REV-06). [M2; not implemented]
- **M4:** the owner-only seal (`owner_seal_root` / `stok_e`) is **replaced in M4 by seal rights for any device holding an admin cert in the log**. M1–M3 keep the owner-only seal, which matches who signs ops there (only the PC owner). The M4 mechanism (how the relay checks a seal without learning ids, and how a removed admin loses seal rights at the next epoch) is specified with M4.

## 9. Opening links
### 9.1 URL policy [M0]
1. Reject raw input containing whitespace, C0/C1 controls, DEL, U+2028/2029, bidi controls (U+202A–202E, U+2066–2069, U+200E/F), zero-width chars or BOM. Nothing is stripped (`UrlBadChars`).
2. Parse with the WHATWG parser (`url` crate) (`UrlParseError`).
3. Scheme `http`/`https` only (`SchemeNotAllowed`; the sender's scheme string is never carried into errors, counters or logs, D11); non-empty host (`UrlMissingHost`).
4. No username/password, and no `@` anywhere in the raw authority (`UrlHasUserinfo`). Host policy (§9.1.1).
5. Canonicalize: re-serialize, percent-encode every byte outside the RFC 3986 set **and every `%` not followed by two hex digits** (`%zz` → `%25zz`, D6/URL-22), require the result to re-parse to itself.
6. `canon.len() ≤ 8192` (or 2048 on the push path) (`UrlTooLong`).
The opener receives exactly `canon` as one argument; the toast shows the ASCII/punycode host from the same `canon`.
#### 9.1.1 Host policy (OQ-8) [M0]
Applied to the host **after** WHATWG parsing, which already normalizes odd IPv4 spellings (decimal `http://2130706433/`, hex `http://0x7f.1/`, octal `http://0177.0.0.1/`, short `http://127.1/`, trailing dot, percent-encoded digits) to dotted-quad, so they hit the same rules.

| Host | Result |
|---|---|
| RFC 1918 (`10/8`, `172.16/12`, `192.168/16`), IPv6 ULA (`fc00::/7`), public addresses and names | **allowed** |
| Loopback: `127.0.0.0/8`, `::1`, `localhost`, `*.localhost` (any case, trailing dot) | `HostLoopback` |
| Link-local: `169.254.0.0/16`, `fe80::/10` | `HostLinkLocal` |
| Unspecified: `0.0.0.0/8` (incl. `0.0.0.0`, `http://0/`), `::` | `HostUnspecified` |
| IPv6 with an embedded IPv4 (`::ffff:a.b.c.d` mapped, `::a.b.c.d` compatible, `::ffff:0:a.b.c.d` IPv4-translated, `64:ff9b::/96` NAT64, local NAT64 `64:ff9b:1::/48` in every RFC 6052 placement, 6to4 `2002:WWXX:YYZZ::/48`) | the IPv4 rules above apply to the embedded address (N1, M1) |
| Deprecated site-local `fec0::/10` | `HostSiteLocal` (N1) |
| `localhost.localdomain`, `ip6-localhost`, `ip6-loopback` (any case, trailing dot) | `HostLoopback` (N1) |
| Multicast `224.0.0.0/4`, `ff00::/8` | `HostMulticast` (N1) |
| Broadcast `255.255.255.255` | `HostBroadcast` (N1) |

**DNS rebinding: accepted risk (QA, M1 decision).** Names are **not resolved** by the policy, so a public name that resolves to loopback (e.g. `127.0.0.1.nip.io`, or a rebinding DNS server) passes and the browser will connect wherever DNS points. Resolving at check time wouldn't help (the browser resolves again later). This is the same exposure as clicking that link on the PC directly; the mitigations are that only paired devices can send and, for users who turn it on, "Ask before opening" (shows the host first; off by default since 10-11-2026). Pinned by a test so a change is deliberate (`url_policy` tests, `127.0.0.1.nip.io` is allowed).

Rationale: links to home-LAN devices (router, NAS, Home Assistant) are a real use case; loopback/link-local/unspecified point at the receiving PC itself or its cloud metadata endpoint, which the sender can't mean. **Revisit in v2** as a user setting (e.g. "allow links to this PC").

### 9.2 Opener [M0]
`UrlOpener::open(OpenApproval)` (by value). An `OpenApproval` has private fields and no `Clone`/`Default`/`From`/serde; it is minted only by `opener::deliver(inbox, url, mode, opener)` in `OpenImmediately` mode and by `PendingOpen::confirm(inbox, opener)` (the user clicked "Open"). Both refuse a `VerifiedUrl` minted by a different `Inbox` (`ForeignInbox`) and re-check the sender's membership in the inbox's roster immediately before opening (`Removed`/`NotInRoster`). `OpenImmediately` is the **default** (THREAT-MODEL §3/§6.2); `ConfirmBeforeOpen` is the desktop setting **"Ask before opening"** (off by default). A fresh PC state starts in no-prompt mode; a saved state keeps its stored choice (M1 state can't tell an untouched default from an explicit "ask first", so a stored "ask" is kept). In no-prompt mode the approval is still minted only by `deliver`, after `Inbox::receive` fully verified the message and after the membership re-check; tests `default_mode_opens_without_prompt_via_deliver`, `ask_before_opening_mode_waits_for_confirm`, `removed_between_verify_and_open_is_refused_in_both_modes`; gate `default-no-prompt-ask-setting`. `SystemOpener` re-runs the URL policy and requires a fixed point before the single OS call. Enforced by compile-fail doctests and `scripts/compile-fail-probes.sh` (QA probe p01, AUTH-17).

### 9.3 Confirm prompts [M1]
- **Expiry (QA M1):** a pending prompt expires **2 minutes** after it arrived (`limits::PENDING_PROMPT_TTL_MS`; a test-only config may shorten it, never lengthen it). `pending()` drops expired prompts; deciding an expired one returns `PromptExpired` and never opens. Deciding an unknown or already-decided id returns `NoSuchPrompt` (it used to say `UnknownDevice`).
- **Confirm window (desktop, QA M1):** it is opened by the network, not the user, so it **never takes focus and is never always-on-top**; it asks for attention (taskbar flash) instead, so a keystroke or click meant for another app can't land on it. **Open** stays disabled for **1 s** after the window appears or its list changes (re-armed on every change and when the window is shown again); the list is updated **in place** (rows are never rebuilt under the pointer); clicks must be trusted events. Gate `confirm-window-no-focus-steal` in `scripts/gates.sh`.

### 9.4 Android share target [M1]
`ShareActivity` is the exported `ACTION_SEND text/plain` target, so **any app can start it with any text**. Starting it never sends (QA M1 High): nothing is sent from `onCreate`, `onNewIntent`, restored state or intent delivery. It shows the link and one **Send to <PC>** button per paired PC (the only, or last-used, PC is the large primary button, so it stays one tap after choosing Voidwire in the share sheet). A tap counts only while the activity is **resumed and its window has focus**, at least **500 ms** after the content appeared (re-armed on resume, focus regain and content change), and never for a touch Android flags as obscured (`filterTouchesWhenObscured` on the window plus a `FLAG_WINDOW_IS_(PARTIALLY_)OBSCURED` check). A re-delivered intent (`onNewIntent`, which Android only delivers while the activity is paused or backgrounded) is ignored and never shown. One tap sends at most once; "Try again" after a failure is another gated tap. Sending goes through an injectable `ShareBackend` (Robolectric tests in `ShareActivityTest`).
**[QA re-check L1]** Any touch Android flags as obscured also **re-arms** the 500 ms delay (so a tap right after an overlay disappears waits again), the finger must go **down after** the button armed (a press begun earlier doesn't count), and on Android 12+ the activity calls `Window.setHideOverlayWindows(true)` (install-time permission `HIDE_OVERLAY_WINDOWS`), so other apps' overlays aren't drawn over it at all. *Residual (API 26-30):* a non-touchable overlay removed without the user touching our window in between can't be observed; the press-after-arming rule and the 500 ms delay remain.
**[QA re-check C1] Native init.** iroh's DNS resolver (and netdev) read Android's network config through JNI and need the JavaVM + application `Context` in `ndk_context` before the first endpoint is built. `Core.phone()` calls `NativeInit.init(applicationContext)` (JNI `Java_app_voidwire_android_NativeInit_nativeInit` in core, installs it once via `iroh::dns::install_android_jni_context`) before `Phone()`. `Phone()` returns `PhoneException.NotInitialized` instead of aborting if that didn't happen, and the Android library is built with `panic = "unwind"` so a Rust panic surfaces as a Kotlin exception at the UniFFI boundary instead of killing the app. Verified on a real Android runtime by `scripts/android-smoke.sh` / `DeviceSmokeTest`.
### 9.5 Open notification [removed in M1.2]
Desktop OS open notifications (`"Opened <host> from <device name>"`), the `"Forget this device"` notification action, `desktop/src/notify.rs`, `tauri-plugin-notification`, and the `"Show a notice when a link opens"` setting were **removed completely in M1.2**. OS notification centers (such as Windows Action Center's `wpndatabase.db`) persist toast notification payloads to disk outside Voidwire's control, which violates Voidwire's "nothing logged unless the user opts in" privacy rule. Gate `no-open-notice` in `scripts/gates.sh` enforces that the notification plugin and open-notice code remain absent.

## 11. Pairwise model, state v2 and relay supervisor [M4.1]
M4 replaces the PC-hosted group with **pairings**: two devices each, every change co-signed by both, each pairing with its own keys, relay and offline inbox. M4.1 ships the core of that model and the on-disk format. **Nothing on the wire changes in M4.1**: every pairing that exists is a *legacy* pairing and still talks the v0.4.x group protocol (§6, §7). Delivery over pairwise keys, the live split and new pairing flows come in M4.2 and M4.3.

### 11.1 Pairing record and log
- `core/src/pairwise/`: a `Pairing` (id, kind, peer cert, origin, relay, per-pairing receive keys, epoch secrets sealed at rest, log) and a two-member log.
- Log ops: `Genesis` (authored by the inviter, co-signed by the joiner), `SetRelay`, `Rekey` (epoch must go up by exactly one), `Caps`, `Rename` (self-signed, own name only) and `Unpair` (self-signed, one-sided, final and applied locally at once). Every other op needs the author's and the peer's signature over the same body and the previous head; ops without a valid co-signature are refused on apply and on load.
- Concurrent proposals: when both sides propose on the same head, the op with the lower hash wins on both sides and the loser is returned for re-proposal, so replicas converge (property test over random interleavings).
- The log compacts to the latest op of each kind; a stored log with a broken chain is refused.
- **Renames [M4.5]** (`core/src/net/pair_ops.rs`): renaming a device signs a `Rename` op in each v2 pairing. It is sent on a v2 connection to the peer that is up, or on the next one that comes up for another reason (no timers, retries or wake-ups); until the peer confirms it, it stays in the stored log and goes out again on each new connection. A rename made before the previous one was sent replaces it. Frame `PAIR_OPS` (0x44): `count u8 ‖ (len u16 ‖ op)*`, oldest first, at most 32; reply `PAIR_OPS_ACK` (0x45) `[status]`: 0 applied or already had, 1 lost a race (the peer's op is on its way; ours is re-signed on top when it lands), 2 refused (not sent again). The receiver checks each op against the pairing log (author is the peer, signature, chain) and shows the new name unless its user set a local nickname. Nothing is logged.

### 11.2 Legacy split (v0.4.x groups)
- A v0.4.x PC group with phones P1..Pn becomes **one legacy pairing per phone**; a phone paired to two PCs gets one per PC. Nothing is re-paired and nothing is sent.
- Pairing id: `SHA-256("voidwire/2026/legacy-pairing-id" ‖ group_id ‖ min(id_a, id_b) ‖ max(id_a, id_b))`, so both ends compute the same id independently.
- The split is recomputed from the group roster on every save: a device removed from the group (Forget, remove op) loses its pairing; a newly paired device gains one. Legacy pairings carry no new secrets; they keep using the group's keys.

### 11.3 State v2
- PC `state.bin` magic `VWPC2\n` (was `VWPC1\n`), phone state magic `VWPH2\n` (was `VWPH1\n`). v2 readers accept both magics.
- New trailing section (PC tag 6, phone tag 7): `u32 length ‖ version 1 ‖ u32 length ‖ pairing set ‖ u32 length ‖ relay settings ‖ 32-byte keyed BLAKE3 MAC`. Epoch secrets inside the pairing set are sealed with a key derived from the device identity secret; the MAC key is derived from the same secret. A damaged section (bad MAC, bad length, unknown version) **fails closed**: the app refuses to start rather than run with silently different pairings.
- A v1 file has no section: the pairings are derived from the group (11.2) and the file is rewritten as v2 on the first save, which happens at start.
- **Downgrade:** v0.4.x apps refuse v2 files (they don't know the new section). Going back to 0.4.x needs a re-pair.

### 11.4 Limits
16 pairings per device, 8 saved relays, 4 relays in use. Pairing a 17th device fails with `pairing_limit_reached` on both sides (the PC checks before admitting a phone, the phone before dialing and again before storing the welcome). Existing pairings above the limit are never dropped.

### 11.5 Relay supervisor
`core/src/relay_supervisor.rs` (pure state machine, tested with an injected clock) and `core/src/net/relay_watch.rs` (runs it against the endpoint):
- A relay that stays disconnected for **30 s is parked**: it is removed from the endpoint's relay map.
- Parked relays are probed with **one TCP connection** (at most one IPv4 and one IPv6 address; the connection is held 750 ms so a load balancer that accepts and closes reads as down) at 30 s, then doubling to a 30 min cap, ±25 % jitter. A successful probe puts the relay back, and the relay then gets **60 s** (not 30 s) to connect before it is parked again, because iroh may still be inside its own reconnect backoff (up to 16 s plus the dial). A relay that passes the probe but never connects keeps its backoff step, so it backs off like a dead one.
- Network change and user action (app opened, retry) retry parked relays at once and reset the backoff.
- Phones in background never retry relays other than the home relay; PCs keep every relay in use live.
- Phones pull their inbox on events only (app open, unlock, network change), at most once per 5 minutes per relay except on app open; never on timers.
- *Known limit (iroh 1.3):* removing the home relay from the map does not stop iroh's own reconnect loop for it (one attempt every 16-32 s: a 16 s backoff cap plus jitter), so parking cuts a dead home relay's connection attempts by about 85-90 % (measured ~165-180 an hour instead of ~1,300-1,450, and no UDP probes) rather than to the probe schedule alone. The supervisor's own probes stay within 8 an hour after parking. Relays that are not an endpoint's home relay (M4.4 away relays, on their own endpoints) stop completely. Measured by `tools/relay-bench` (TEST-PLAN §13).

### 11.6 Lighter background check (experiment, off by default)
Behind an internal switch (`set_light_background_checks`, no UI): while a phone is in background, the home relay is re-inserted **without QUIC address discovery**, which is most of the idle packet traffic. Direct (IP) paths stay enabled. It stays only if direct connections still work; `tools/relay-bench` measures both.

## 12. v2 delivery and the live split [M4.2]
- **Any peer:** a phone accepts app connections from any device it has a v2 pairing with (PC or phone); PCs connect to PCs and phones to phones. Messages on a v2 pairing are sealed and checked with that pairing's keys and log, not the legacy group's.
- **Offline inboxes:** each side of a v2 pairing has its own blind inbox on the **pairing's relay** (the inbox id and keys come from the pairing secret, so a third device cannot derive or ack them; B10 test). A send that cannot reach the peer live is queued there.
- **Pulls (events only, no timers):** one session per relay pulls every inbox on that relay. Phones pull on app open, unlock and network change (at most once per 5 minutes per relay except on app open). PCs pull at start and when the Devices window gets focus (at most once per 5 minutes).
- **Unpair:** `Unpair` is sent as a notice message (live, or queued in the peer's inbox); the receiver erases the pairing and its keys.
- **Live split** of a legacy pairing (app ALPN, phone asks, PC answers; frames carry `u16 length ‖ bytes` fields):

  | Phone → PC | PC → phone |
  |---|---|
  | `SPLIT_REQ 0x30` (empty) | `SPLIT_READY 0x31` (empty); a PC before M4.2 answers `ERROR` and the pairing stays legacy |
  | `SPLIT_JOIN 0x32`: phone cert, fresh per-pairing receive key | `SPLIT_OFFER 0x33`: PC-signed genesis (relay = the PC's relay), `gs_0` wrapped to that key |
  | `SPLIT_ACCEPT 0x34`: co-signed genesis, `Caps(V2)` | `SPLIT_CAPS 0x35`: co-signed `Caps`; the PC stores the v2 pairing |
  | `SPLIT_DONE 0x36`: pairing id (after the phone stored it and dropped the legacy copy) | `RESULT`; the PC removes the phone from the legacy group (Remove + Rekey) |

  The phone runs the split when the app comes to the front, once per PC per run, never in background. If `SPLIT_CAPS` is lost the PC keeps accepting the phone's legacy messages until the phone asks again (a retry replaces the half-made pairing); if `SPLIT_DONE` is lost the PC retires the legacy membership on the phone's first message over the new pairing. Phones that have not moved yet keep working on the (rekeyed) legacy group.
- **DTOs:** the desktop IPC and send-error metadata name the target `device_id` only; the old `phone_id` / `phones` names are gone (no back-compat before launch).
